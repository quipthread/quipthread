---
title: Docker deployment
description: Run Quipthread with Docker Compose, Caddy HTTPS, and optional SQLite backups.
---

Docker Compose runs Quipthread and Caddy on your server. Quipthread stores comments and account data in a persistent SQLite volume. Caddy handles HTTPS.

You need Docker Engine with the Compose plugin, a Linux AMD64 or ARM64 server, and a domain pointing to that server. Allow inbound TCP ports 80 and 443. UDP port 443 is optional for HTTP/3.

## 1. Get the deployment files

```bash
git clone https://github.com/quipthread/quipthread
cd quipthread
cp .env.docker.example .env
chmod 600 .env
```

The repository provides `.env.docker.example` as the Docker configuration template.

## 2. Configure the instance

Generate a secret with `openssl rand -hex 32`, then edit `.env`:

```dotenv
JWT_SECRET=replace-with-your-generated-secret
BASE_URL=https://comments.example.com
ALLOWED_ORIGINS=https://publisher.example.com
DATABASE_URL=/data/db.sqlite
PORT=8080
TRUST_PROXY=true

GITHUB_CLIENT_ID=replace-with-your-client-id
GITHUB_CLIENT_SECRET=replace-with-your-client-secret
```

Set `BASE_URL` to the address of Quipthread. Set `ALLOWED_ORIGINS` to the exact origins of the websites that embed comments, separated by commas. Include the scheme and any non-default port; omit paths and wildcards. Dashboard requests from `BASE_URL` are accepted separately.

Configure GitHub, Google, or [email authentication](/docs/guides/email-auth/). Register OAuth callbacks as `https://comments.example.com/auth/github/callback` or `https://comments.example.com/auth/google/callback`. See [OAuth setup](/docs/guides/oauth-setup/) and the [environment variable reference](/docs/reference/environment-variables/).

Keep `PORT=8080` with the supplied Caddy configuration. `TRUST_PROXY=true` lets rate limiting use the client IP forwarded by Caddy. The Compose file keeps the app port private; expose it only through your trusted proxy.

## 3. Configure HTTPS

Edit `deploy/Caddyfile`: replace `example.com` with `comments.example.com` and replace the example email address. Keep the existing proxy and header configuration.

Point your domain's DNS records to this server. Caddy obtains and renews a certificate automatically. If you use another proxy or CDN, ensure it permits certificate validation and routes traffic to Caddy.

## 4. Choose an image and start

### Use the published release

```bash
docker compose pull
docker compose up -d
```

The Compose file uses `ghcr.io/quipthread/quipthread:latest`. This tag changes when a public `v*` tag triggers the release workflow; merging code into `main` does not publish a new image. For repeatable deployments, set the app image in `docker-compose.yml` to a published version tag or digest.



### Build the checked-out source

Create `compose.source.yml`:

```yaml
services:
  app:
    image: quipthread:selfhosted-local
    build:
      context: .
      dockerfile: Dockerfile
```

Then run:

```bash
docker compose -f docker-compose.yml -f compose.source.yml build app
docker compose -f docker-compose.yml -f compose.source.yml up -d
```

Use the same two `-f` options for subsequent Compose commands when running this local image. Docker builds the dashboard, embed widget, and backend, and packages the pinned Atlas migration CLI. You do not need Go or Bun installed on the host.

## 5. Verify startup

```bash
docker compose logs --tail=100 app caddy
curl --fail https://comments.example.com/health
```

The health response should report `status: ok` and `database: ok`. Open `https://comments.example.com/login`, sign in, and create a site in the dashboard. The first account receives admin access, so complete this step before sharing the instance publicly.

Follow the [embed setup instructions](/docs/guides/self-hosting/#5-embed-the-widget) to add comments to your website.

## Test locally without HTTPS

Use a separate checkout and Compose project for testing. Configure real OAuth credentials with a localhost callback, or configure email authentication with a test SMTP server. Then publish the app port explicitly:

```bash
docker compose run --rm --no-deps \
  --publish 127.0.0.1:8080:8080 \
  -e BASE_URL=http://localhost:8080 \
  -e ALLOWED_ORIGINS=http://localhost:8080 \
  -e TRUST_PROXY=false \
  app
```

Open `http://localhost:8080/login`. If your test website uses another port, include that origin in `ALLOWED_ORIGINS`. This checks local startup and dashboard access; use HTTPS to test cross-site authentication in its production configuration.

The app service has no host port mapping by default, so `--service-ports` alone does not expose it. Do not run a second app container against a database already in use.

## Back up SQLite with Litestream

The image packages Litestream v0.3.14. Set these variables in `.env` to enable replication:

```dotenv
LITESTREAM_REPLICA_URL=s3://your-bucket/quipthread/db.sqlite
LITESTREAM_ACCESS_KEY_ID=replace-with-your-access-key
LITESTREAM_SECRET_ACCESS_KEY=replace-with-your-secret-key
```

Restart the app after changing its environment. The entrypoint generates `/tmp/litestream.yml` from these variables. Editing a host-side `deploy/litestream.yml` has no effect on this setup.

On startup, the entrypoint restores from the replica only if the local database is absent. It checks the integrity of a restored database before starting Quipthread. Restore errors stop startup; a missing replica allows a fresh database to be created.

Replication is asynchronous. Recent writes may be lost if they have not reached the replica, and a misconfigured backup may contain no usable data. Check replication logs and test a restore before relying on it. Keep an independent backup before upgrades.

For a separate-target restore and validation procedure, use the [self-hosted restore runbook](https://github.com/quipthread/quipthread/blob/main/docs/runbooks/self-hosted-restore.md). Custom S3 endpoints may need additional Litestream configuration; the supplied entrypoint does not accept an endpoint variable or a mounted config file. No MinIO Compose overlay is included.

## Upgrade

Back up the database, then pull the next published image and recreate the service:

```bash
docker compose pull
docker compose up -d
```

For source builds, update your checkout and repeat the source-build commands instead. Startup verifies Atlas and runs database migrations before serving requests. If migration fails, inspect the app logs before retrying.

The named data volume survives container replacement and `docker compose down`. **Do not use `docker compose down -v` to upgrade:** it deletes the database volume and Caddy's certificate storage. An older image may not support an upgraded database; retain a matching pre-upgrade backup for rollback.
